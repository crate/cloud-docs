Configure CrateDB Enterprise Edition
---------------------------------------

To launch the setup, simply run the following commands once the package has been installed:

.. code-block:: bash

   cd /opt/crate/cratedb-ee-console
   sudo installer/setup.sh

The setup script will ask some questions to help identifying the right configuration.

Connection to the CrateDB cluster
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The URL to the cluster and a CrateDB user name and password will be asked.
Please note that the given CrateDB user credentials must be able to authenticate from this host.

Configuration of a truststore
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

CrateDB Enterprise Console relies on the truststore in the CrateDB cluster for its own authentication purposes and this
step will help set it up.

It is recommended you use the already present truststore, if available. If you want to override it, make sure you make a
backup of the existing truststore first.

The setup script will first ask whether the CrateDB cluster already has a truststore set up.

You can select one of the following paths:

- Let the setup create a new ``CA`` certificate and a new truststore storing that certificate.
- Provide an already existing ``CA`` certificate and let the setup create a truststore that stores it.
- Provide a ``CA`` certificate stored in a truststore already installed in the CrateDB server.

Please note the certificate used to serve the CrateDB Enterprise Console to the browser will be signed by the ``CA``
certificate stored in the truststore. This means you will see a warning in the browser if it does not trust the
``CA`` certificate.


When a truststore is already set up on CrateDB
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

If a trust store is already set up in the CrateDB cluster, the files ``ca.crt`` and ``ca.key`` contained in it will need
to be copied to the locations given by the setup script. This is necessary because CrateDB EE
uses certificate based authentication and the setup script will use these files to generate
the required certificates.

Once the certificates have been generated, the ``ca.crt`` file is still needed for authorization purposes.

When CrateDB does not have a truststore set up
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

If a trust store is not configured in the CrateDB cluster, the setup script will generate one.
The script will first ask whether you already have a ``ca.crt`` you would like to use as the
certificate authority for the new truststore. Answering yes lets you supply your own ``CA``;
answering no makes the script generate a new self-signed ``CA`` to issue the certificates from.

The script will then ask for a truststore password and a keystore password, used to protect
the generated ``truststore.p12`` and ``keystore.p12`` files, respectively. Please keep these passwords, as they are
needed again when configuring the CrateDB cluster below.

Distribute the truststore to the CrateDB cluster
""""""""""""""""""""""""""""""""""""""""""""""""""

If a truststore has been generated by the script, you must copy its files to each CrateDB
node of your cluster. Before you do that please make sure you are not accidentally overriding
any truststore already present in the cluster.

Once the setup script has finished, copy ``keystore.p12`` and ``truststore.p12`` from
``/etc/opt/crate/cratedb-ee-console/ca/`` to every CrateDB cluster node, for example:

.. code-block:: bash

   scp /etc/opt/crate/cratedb-ee-console/ca/truststore.p12 <user>@<cratedb-node>:<path>
   scp /etc/opt/crate/cratedb-ee-console/ca/keystore.p12 <user>@<cratedb-node>:<path>

The official CrateDB container certificate path is ``/certs/``.

Please note these commands assume the CrateDB EE Console machine can access via the default port SSH
all the CrateDB nodes. Depending on your system configuration this will not be the case.

CrateDB must be able to read these files. The official CrateDB container image runs as
uid ``1000``, so once the files are in place on the node, make sure they are owned by, or
readable by, that user, for instance ``chown 1000:1000 truststore.p12 keystore.p12``.
A keystore that CrateDB cannot read will write to its logs a ``keystore password was incorrect``
error.

Apply the configuration to the CrateDB cluster
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A configuration stub to help configure the CrateDB nodes will be generated by the script
and can be found at ``/etc/opt/crate/cratedb-ee-console/cratedb-config.txt``
It looks similar to:

.. code-block:: yaml

   - -Cauth.host_based.enabled=true
   - -Cauth.host_based.jwt.iss="https://<cratedb-ee-console-host>:9443/api/v2/meta/jwk/"
   - -Cssl.http.enabled=true
   - -Cssl.psql.enabled=true
   - -Cssl.keystore_filepath=<path to keystore.p12 on the CrateDB node>
   - -Cssl.keystore_password=<keystore password>
   - -Cssl.keystore_key_password=<keystore password>
   - -Cssl.truststore_filepath=<path to truststore.p12 on the CrateDB node>
   - -Cssl.truststore_password=<truststore password>
   - -Cauth.host_based.config.10_ee_console.user=grand_central
   - -Cauth.host_based.config.10_ee_console.ssl=on
   - -Cauth.host_based.config.10_ee_console.method=cert
   - -Cauth.host_based.config.20_issuer.address=<cratedb-ee-console-host>/32
   - -Cauth.host_based.config.20_issuer.protocol=http
   - -Cauth.host_based.config.20_issuer.method=password
   - -Cauth.host_based.config.30_users_jwt.protocol=http
   - -Cauth.host_based.config.30_users_jwt.method=jwt

Add these settings to each CrateDB node configuration (for example the ``command`` section
of CrateDB's ``docker-compose.yaml``, or ``crate.yml``), then restart every CrateDB node for the
new configuration and TLS certificates to take effect.

Please make sure there are no name collisions with any existing host based authentication
configuration your CrateDB may already have (the ``30_users_jwt`` part, for instance).

Reaching the CrateDB EE Console
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The setup script will ask for the host name or IP that will be used by end users to connect to the CrateDB EE.
This is required to properly generate the SSL certificate that will be served by the web server.

In the case of users that are to access CrateDB EE via port forwarding into the machine, localhost is valid.

Otherwise, the value must be the hostname or IP that the users will have to type in their browser to access CrateDB EE.

Please note this may be different from the IP or domain of the machine, depending on your setup.

Clean up
~~~~~~~~~

Once the setup script has completed, and the certificate files have been copied to every
CrateDB node and applied to the CrateDB configuration, delete the following files from the
CrateDB EE Console machine, as they are no longer needed there and contain sensitive key material:

- ``ca.key``
- ``keystore.p12`` (if present)
- ``truststore.p12`` (if present)

These files live under ``/etc/opt/crate/cratedb-ee-console/ca/``.


.. stepper::

Start, stop and restart CrateDB Enterprise Edition
----------------------------------------------------

Once CrateDB has been configured and restarted with the settings above, start the
CrateDB EE services:

.. code-block:: bash

   sudo systemctl start cratedb-ee-mgmt

Use the following commands to stop and restart CrateDB Enterprise Edition:

.. code-block:: bash

   sudo systemctl stop cratedb-ee-mgmt
   sudo systemctl restart cratedb-ee-mgmt


Access CrateDB Enterprise Console
-------------------------------------

CrateDB EE is now reachable at ``https://<hostname>:9443``, using the hostname or IP
address given during setup.


Changing the CrateDB Enterprise Console configuration manually
----------------------------------------------------------------

The setup script will automatically generate a configuration that should work.
It is recommended to rely on the setup script.

The file ``/etc/opt/crate/cratedb-ee-console/config.sh`` stores the configuration.

The following variables can be changed:

- CRATEDB_EE_FRONTDOOR: Full URL that points to the CrateDB Enterprise Console web app using SSL.
- CRATEDB_EE_FRONTDOOR_HTTP: Full URL that points to the CrateDB Enterprise Console web app using plain HTTPS. It will redirect to its SSL counterpart.
- CRATEDB_EE_CRATEDB_EXTERNAL_URL: Full URL that points to the CrateDB cluster (either a load balancer or one of its nodes). The protocol must be HTTPS.
- CRATEDB_EE_DNS: The hostname (or static IP) that represents the CrateDB cluster load balancer or one of its nodes.
- CRATEDB_EE_MINTER_ISS: Full URL with the structure http://iss_hostname:8080/api/v2/meta/jwk/ where iss_hostname is the container that mints the authentication tokens.
  Please note this URL will be part of the token as the ISS field and must exactly match the ``auth.host_based.jwt.iss`` configuration parameter in the CrateDB cluster, otherwise login attempts will fail.
- CRATEDB_EE_ONPREM_CLUSTER_ID: The Cluster ID of the CrateDB cluster.

To apply any change to the configuration, the following commands must be executed:

.. code-block:: bash

   sudo systemctl stop cratedb-ee-mgmt
   sudo /opt/crate/cratedb-ee-console/installer/install-images.sh
   sudo systemctl start cratedb-ee-mgmt


Troubleshooting
-----------------

Login failures
~~~~~~~~~~~~~~~~

The most common issues related to login failures are:

- The ``CRATEDB_EE_MINTER_ISS`` not matching exactly (including the protocol) the ``auth.host_based.jwt.iss`` CrateDB authentication configuration.
- The ``CRATEDB_EE_ONPREM_CLUSTER_ID`` not matching the CrateDB cluster ID. Check your CrateDB cluster ID by executing the query ``SELECT id FROM sys.cluster``.
- A CrateDB authentication configuration rule is not correct.

Look for login issues in the CrateDB logs.
Alternatively, look for login issues in the CrateDB Enterprise Console minter:

.. code-block:: bash

   journalctl -u systemctl status minter

Make sure the IP specified in the CrateDB configuration and the IP of the CrateDB Enterprise Console seen by the CrateDB cluster are the same.
